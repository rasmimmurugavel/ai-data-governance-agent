How the Data Quality & Governance Agent actually works

A step-by-step, diagram-first tour of the whole system — Streamlit + Claude + MCP + Postgres — for someone who has never seen it before. What each piece does, exactly where the AI is involved, what it costs, and how to use less of it.

01 · The problem, in plain English

What are we actually building?

Companies keep their important data — customers, orders, transactions — in databases. Over time those databases get messy: some fields are left blank, the same customer gets entered twice, an order points to a customer that was deleted, a hidden column full of email addresses nobody remembers is personal information. Finding and reporting on this stuff, over and over, by hand, doesn't scale.

So we built a tool that does it automatically: you click one button, and an AI (Claude) looks at your database, decides what to check, runs those checks, and writes a report — a bit like a very fast, very consistent junior data-quality analyst.

The catch: an "AI that pokes around your production database" sounds risky. So almost everything about how this is built exists to make that safe and provable — the AI can only read (never write), it never sees a real email address or phone number, and every single thing it does is written to a permanent log. That combination — safe by construction, plus a paper trail — is what "audit-ready" means here.

Three moving parts, one job each: a website you click buttons on (Streamlit), an AI that decides what to investigate (Claude), and a locked-down toolbox of database operations the AI is allowed to use (MCP server). None of the three can do their job without the other two.

02 · The five pieces and how they talk

Architecture, end to end

Follow the diagram top to bottom. The teal boxes are where the actual "thinking" happens (the browser and Claude); the blue boxes are the governed data layer — the part that's locked down and logged.

Walking through it in words

  1. 1

    You click "Run Audit" in the browser. Streamlit calls a Python function — nothing has happened with your data yet.

  2. 2

    The Agent Engine asks Claude "here's the database, here's your instructions, go" — this is the first real network call, over the internet, to Anthropic's API.

  3. 3

    Claude replies "call this tool" — e.g. inspect_schema or profile_table — instead of writing an answer directly.

  4. 4

    The Agent Engine relays that request to the MCP Server — a separate little program running on the same machine, talking over a local pipe, not the internet.

  5. 5

    The MCP Server runs a real, read-only SQL query against Postgres — but only after checking it's a plain SELECT, that the target table is in an allowed list, and capping how many rows can come back.

  6. 6

    Before the result goes anywhere else, the MCP Server masks anything that looks like personal information, writes one line to the audit log describing exactly what just happened, and only then hands back a safe summary.

  7. 7

    That safe result goes back to Claude (steps 2–6 repeat — sometimes a handful of times, sometimes dozens) until Claude decides it has checked enough.

  8. 8

    Claude's final reply is a structured report — scores, findings, severities — which the Agent Engine hands to the browser to render as charts and a downloadable file.

04 · What "data quality" and "governance" mean here

The framework, in plain language

Every table gets scored 0–100 on five dimensions, then rolled up into one grade.

🧩Completeness

Are the boxes filled in? (missing emails, blank dates)

✅Validity

Does the data make sense? (no negative ages, no fake dates)

🔁Uniqueness

Any accidental duplicates? (same customer, twice)

🔗Consistency

Do linked tables agree? (an order pointing to a deleted customer)

⏱️Timeliness

Is it fresh, or has a pipeline quietly stopped updating?

"Governance" adds three more guarantees on top of the scoring:

🕶️ Privacy

Before anything reaches Claude, a filter disguises anything PII-shaped: jane@x.com becomes j***@***.com. This happens in plain Python, in mcp_server/tools/pii.py — not something we merely ask the AI to do.

🧾 Proof

Every question the AI ever asks the database is written to a permanent log — even ones that don't end up in the final report. An auditor can independently reconstruct exactly what happened.

🎯 Trust

Before a new version ships, it's graded against 4 practice databases with known-correct answers. Miss too much, or leak one PII value, and it fails the test — a rule, not a hope.

05 · Where the AI is actually involved

Where Claude comes in — and where it doesn't

There are exactly two buttons in the app that ever talk to Claude's API over the internet:

  • Inspect Schema — one short exchange with Claude, mostly just reading table structure.
  • Run Audit — the main event. Claude has a back-and-forth conversation with itself: decide what to check → call a tool → read the result → decide what's next. This can be anywhere from a handful to around 40 separate exchanges (a configurable safety cap, so it can't run forever).

Everything else is 100% ordinary code. The SQL queries, the null counts, the duplicate checks, the orphaned-link checks — all plain Python and SQL, computed by deterministic code with zero AI involved. Claude's only two jobs are: (1) decide what to check and when to stop, and (2) turn raw numbers into a written judgment call (a severity, a plain-English description). It never writes a query by hand for the fixed checks — it just calls tools that already exist.

06 · What "audit-ready" is actually buying you

Four guarantees, not a slogan

  1. 🔒

    Read-only, enforced twice. The database login itself can't write — and even if it somehow could, a separate code-level check independently blocks anything that isn't a plain read.

  2. 🕶️

    PII masked before the model ever sees it. Not a prompt asking Claude to behave — a hard filter in the code, upstream of every API call.

  3. 🧾

    Every action logged, independent of the report. The log is the source of truth for "what actually happened," separate from — and stricter than — whatever the AI chose to summarize.

  4. 📐

    Output shape is contractually checked. If Claude's final answer doesn't match the exact expected structure, the run is thrown out rather than shown to you as if it were trustworthy.

07 · If you want to use as little AI as possible

Three modes, from full agent to zero LLM

The 4 baseline checks (nulls, duplicates, broken links, PII) are already plain Python functions in mcp_server/tools/. Nothing stops you from calling them directly, without ever asking Claude to decide to.

as built
Full Agent
SQL checks → Claude × 10–40 → report

Claude decides what to check, in what order, and when to stop. Most thorough and adaptive — it can notice things nobody thought to hard-code a rule for.

~$0.10 – $0.50 per audit
recommended middle ground
Hybrid / Guided
SQL checks → Claude × 1 → report

Run every baseline check yourself with a plain Python script (no AI, no decision-making needed for fixed checks) — then make exactly one Claude call at the end, handing it the raw numbers and asking for the write-up and severities.

~$0.01 – $0.03 per audit
zero AI
Classic DQ Dashboard
SQL checks → Claude → report

Skip Claude entirely. Run the SQL checks, apply fixed thresholds you write yourself ("flag if nulls > 5%"), show the numbers. Free, but it can only ever catch what you explicitly told it to look for.

$0 API cost

The Hybrid mode is usually the sweet spot: 10–20× cheaper than the full agent, still gets a written, judgment-based report instead of a raw numbers table, and is a small code change — not a rewrite — since the underlying checks are already separate, callable functions.

08 · What this costs to run in production

Cost estimate

Split into two very different lines: the AI API bill (small, and the part people worry about most) and infrastructure (hosting the app and the database — usually the bigger line).

1. Claude API cost, per audit

Based on Claude Sonnet 5 pricing: $2.00 per million input tokens, $10.00 per million output tokens. Each turn in the loop re-sends the growing conversation so far — that's how the API works — so the total moves more tokens than it looks like from the outside.

The honest way to know for sure is to run a week of real audits and read the actual numbers off the Anthropic Console usage dashboard, rather than trust anyone's estimate, this page included.
